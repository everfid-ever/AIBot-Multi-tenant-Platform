# 故障恢复后继续对话 — 概念与边界

## 场景与承诺

同一企业微信用户分别与 Bot A、Bot B 建立原会话并留下不同测试代号。节点退出后，存活实例能继续接收新消息、读取该租户/应用/会话已经提交的上下文，并按原 Bot 目的地回复。处理故障前旧在途消息另由第二项能力判定，不以一条新回复代替原工作完成。

当前通过可信 Binding、租户 HMAC 身份、持久 Inbox/输入、平台顺序与官方 SDK 分域、权威终态历史和原回复路由实现。WeCom 使用 HTTP callback；入口健康切换不等于某个 Bot 长连接所有权迁移。

## 三个具体数字

| 数字 | 含义与条件 |
|---|---|
| 2个 Bot | 本地组合根的两个独立租户/绑定，同一存活实例能服务两者 |
| 最多100个输入终态 | 当前原会话历史读取窗口；有序连续核验，不是无限记忆 |
| 1份有效终态 | 同一原输入只有一个有效terminal；可见最终回复仍受渠道协议边界约束 |

## 业务故事怎样落到数据

1. 渠道验证后才确认 tenant/app/binding；不相信消息自报租户。
2. 同部署秘密版本和原账号/会话坐标派生同一 user/session，节点ID不参与派生。
3. 新消息沿原会话分配新的 input_seq；旧未完成输入先完成或明确终结，后续输入不能越序提交。
4. 历史按 session_commit、原成功输入和精确冻结结果构造，不把SDK最高Fence草稿当过去答案。
5. 原 request + 原 Inbox/配置恢复 Binding/目标，发送与用户归属交叉核验。

## 范围与不包含

共享PG/Redis、原版本秘密/配置和存活实例承载能力是前提。未被服务端可靠接收的消息、无限上下文、模型必然正确回忆、任意主机/依赖整体故障、无条件客户端恰好一次不在承诺内。同Corp不同Agent的两Bot可有相同external_account_id，仍由不同tenant/绑定/密钥隔离，不能只比CorpID判断。
